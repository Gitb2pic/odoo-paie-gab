## 2. Prêts (F1, RG19-RG21)

| Modèle | Champs |
|---|---|
| `l10n_ga.employee.loan` (`mail.thread`, `mail.activity.mixin`) | `name` (séquence `PRET/2026/…`, déjà en données), `employee_id` (`check_company`), `company_id`, `currency_id`, `date` (octroi), `amount`, `installment_count`, `first_due_date` (1er jour du mois), `installment_amount` (calculé), `state` brouillon / approuvé / en cours / soldé / annulé (suivi), `derogation`, `derogation_reason`, `derogation_user_id`, `derogation_date`, `eligibility_issues` (texte calculé, non stocké, affichage seulement), `line_ids`, `remaining_amount`, `withheld_amount` (stockés) |
| `l10n_ga.employee.loan.line` | `loan_id`, `company_id` (related stocké), `employee_id` (related stocké), `due_date`, `amount`, `state` à payer / retenue / reportée / **remboursée hors paie** (P5), `payslip_id` (RG21 : au plus un bulletin), `note` |

Cycle (patron State, transitions gardées) :
- **brouillon** → bouton « Calculer l'échéancier » (mensualités égales arrondies au franc, la dernière absorbe l'écart) ;
- **approuver** : spécifications `MinSeniority & MaxInstallmentRatio & MaxOutstanding` (noyau pur, paramètres datés à la date d'octroi + plafond société `l10n_ga_loan_outstanding_cap`, 0 = pas de plafond) ; échec → refus avec les motifs, sauf dérogation cochée **avec motif obligatoire** (utilisateur, date et motifs levés tracés dans le chatter) ; seul le groupe « Paie : responsable » approuve ;
- **en cours** à la première échéance retenue ; **soldé** quand plus rien n'est « à payer » ; **annulé** seulement si aucune échéance retenue.
- **Reporter** une échéance : elle passe « reportée », une échéance de même montant est ajoutée un mois après la dernière (P6).
- **Remboursement anticipé** (assistant) : montant ≤ restant ; mode « hors paie » (échéance « remboursée hors paie » datée) ou « sur le prochain bulletin » (échéance à payer au mois choisi) ; les échéances restantes sont réduites **en partant de la fin** (la durée raccourcit, la mensualité ne change pas).

Paie :
- `compute_sheet()` → `_l10n_ga_loan_inputs()` **avant** le calcul (sprint 0 point 6) : supprime les entrées `GA_LOAN` automatiques du bulletin brouillon, crée une entrée par échéance « à payer » dont la date tombe dans la période (prêt approuvé ou en cours) ; `GA_LOAN` n'est pas `available_in_attachments` (déjà vrai, testé en 2.2) ;
- **bulletin de départ** (départ ou fin de contrat dans la période, comme la régularisation IRPP) : **tout le restant dû** est proposé, plafonné à la quotité saisissable (P4) ; le reste demeure « à payer », une activité est créée pour le gestionnaire du prêt ;
- `action_payslip_done()` : échéances du bulletin → « retenue », `payslip_id` renseigné (RG21, P2) ; `action_payslip_cancel()` / `action_payslip_draft()` : retour « à payer ».

## 3. Indemnités récurrentes (F15, RG28) — extension de `hr.salary.attachment` (ADR-16, P1)

Le prompt prévoit `l10n_ga.employee.allowance` **ou**, si l'ajustement standard accepte les gains, son extension : c'est le cas (sprint 0 point 9, ADR-16 accepté) → **pas de nouveau modèle**.

| Champ ajouté | Rôle |
|---|---|
| `l10n_ga_mode` | `fixed` (montant, défaut) / `wage_percent` (% du salaire de la version du bulletin) / `quantity_rate` (quantité × taux) |
| `l10n_ga_rate`, `l10n_ga_quantity` | pourcentage ou taux unitaire ; quantité |
| `monthly_amount` | inchangé en mode fixe ; en mode calculé : montant indicatif calculé et stocké (la contrainte SQL `> 0` reste valable) |
| `l10n_ga_forced_taxable`, `l10n_ga_forced_reason` | forcée imposable ; motif obligatoire (`@api.constrains`) |
| `l10n_ga_is_ga` | type d'entrée Gabon (affichage du bloc) |

- **RG28** (`@api.constrains`) : pour un même salarié et un même type, deux ajustements ouverts ne se chevauchent pas (fin vide = sans limite). Revalorisation = clôture + nouvelle ligne datée.
- `hr.payslip._l10n_ga_allowance_inputs()` (appelée par `_compute_input_line_ids` après le standard, et par `compute_sheet` avant le calcul) : pour les bulletins Gabon, remplace l'entrée groupée du standard par **une entrée par ajustement**, marquée `l10n_ga_allowance_id`, montant = valeur du mode × **prorata des jours calendaires de validité** dans la période (P7) ; **une entrée manuelle du même type** (non marquée) **supprime l'automatique** ; la proratisation par la présence reste celle de la règle (`l10n_ga_prorate`, ADR-16 §4).
- **Forcée imposable** : `l10n_ga_forced_taxable` recopié sur l'entrée ; `_l10n_ga_gain_lines()` scinde le total de la règle au prorata des entrées forcées / non forcées → `GainLine(forced_taxable=True)` (P8) ; le figement par ligne (F16) regroupe par code.

## 8. Risques

- `_compute_input_line_ids` standard efface les saisies manuelles d'un type d'ajustement quand les dates du bulletin changent : comportement natif, documenté ; la priorité manuelle vaut pour les saisies faites sur le bulletin calculé.
- Ajustements multi-salariés (`employee_ids`) en mode « % du salaire » : montant calculé par bulletin, donc juste ; le montant indicatif est celui du premier salarié.
