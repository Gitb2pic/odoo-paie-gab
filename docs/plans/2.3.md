## 4. `hr.payslip` — adaptateur (patron 2) et bulletin figé (F7)

Méthodes :
- `_l10n_ga_is_ga()` : structure du bulletin = type « Gabon : Employé » ;
- `_l10n_ga_params()` : `{code: _rule_parameter(code)}` pour chaque `ParamSpec` + options société (`cash_rounding`, `cfp_base`) → `params_from_values` (table unique `param_codes`) ;
- `_l10n_ga_paid_ratio()` : `paid_amount / _get_contract_wage()`, borné à [0, 1] (1 si salaire nul) — même proratisation que `BASIC` ;
- `_l10n_ga_days_worked()` : jours des `worked_days` dont la prestation n'est pas une absence (`is_leave` faux) → exonération transport journalière ;
- `_l10n_ga_ytd(field)` : somme d'un champ figé sur les bulletins `validated`/`paid` du salarié, même année civile, `date_to` < `date_from` du bulletin (état standard, sprint 0 point 3) ; les cumuls d'ouverture F12 s'y ajouteront en 2.6 ;
- `_l10n_ga_regularize()` : dernier bulletin de l'année (`date_to` = 31/12) ou départ (`departure_date` ou `contract_date_end` de la version dans la période) ;
- `_l10n_ga_facts(result_rules)` : une `GainLine` par règle de la structure ayant `l10n_ga_social_base != 'none'`, hors catégorie `GA_AIK`, total ≠ 0, groupes par `treatment.social_group` / `tax_group` ; avantages en nature = drapeaux de la version ; `main_salary` = `BASIC` ; parts, enfants, trajets, véhicule depuis `version_id` ; cumuls `ytd_bonus_exempted`, `ytd_irpp_base`, `ytd_irpp_withheld` ;
- `_l10n_ga_compute(code, categories, result_rules)` : `PayResult` mis en cache dans `cr.cache` par bulletin, clé = `PayslipFacts` (dataclass figée, hachable) ; les données fixes du bulletin (paramètres, version, cumuls) sont lues une fois par calcul ; cache purgé en tête de `_get_payslip_lines`. `code` = attribut de `PayResult` ou `benefit:<nature>`.

Champs (tous stockés, lecture seule, remplis à la validation — surcharge de `action_payslip_done` **avant** `super()`, sprint 0 point 13) :

| Champ | Contenu |
|---|---|
| `l10n_ga_payment_date` | Date de paiement (saisie ; défaut `date_to`) — utilisée par l'ID10 (étape 4) |
| `l10n_ga_tax_parts_used`, `l10n_ga_marital_used`, `l10n_ga_children_used` | situation retenue |
| `l10n_ga_cnss_ceiling_used`, `l10n_ga_cnamgs_ceiling_used` | plafonds appliqués |
| `l10n_ga_gross`, `l10n_ga_benefits_in_kind`, `l10n_ga_social_base`, `l10n_ga_taxable_gross`, `l10n_ga_tcs_base`, `l10n_ga_irpp_base` | bases |
| `l10n_ga_social_excluded`, `l10n_ga_tax_exempt`, `l10n_ga_bonus_exempted` | exonérations du mois |
| `l10n_ga_cnss_employee`, `l10n_ga_tcs`, `l10n_ga_irpp_withheld` (IRPP + régularisation) | retenues du mois (lecture DAS/cumuls) |
| `l10n_ga_ytd_gross`, `_taxable`, `_irpp_base`, `_irpp`, `_tcs`, `_cnss`, `_bonus_exempt` | cumuls annuels **incluant** ce bulletin |
| `l10n_ga_frozen_date` | date du figement |

Les valeurs figées sont recalculées depuis les **lignes** du bulletin (`{code: total}`) ; si le noyau, rejoué avec les paramètres du jour, ne retrouve pas les montants des lignes fiscales (paramètre modifié entre calcul et validation), la validation est refusée (`UserError` : « recalculer le bulletin »). Un bulletin validé ne relit jamais les paramètres : réimpression et DAS lisent les champs figés (F7). `l10n_ga_rounding_carry` (F2) est reporté à l'étape 2.6 avec les règles d'arrondi espèces.

`hr.payslip.line` : `l10n_ga_social_excluded`, `l10n_ga_tax_exempt` (Monetary, stockés) écrits à la validation depuis `PayResult.lines` (F16) ; les lignes d'avantages en nature du noyau (`AN_HOUSING`…) sont rattachées à `GA_AN_LOGT`… par la table du catalogue.

## 5. Règles salariales liées au noyau

### 5.1 Catalogue

Nouveau genre `core` et colonne `core_value` (attribut de `PayResult`). Formule générée, une seule ligne, sans nombre :
`result = -payslip._l10n_ga_compute('<core_value>', categories, result_rules)` (retenues, signe négatif) ou sans signe (charges patronales, avantages en nature). Condition « montant non nul » pour `GA_IRPP_REGUL` et `GA_FNH_SAL`.

| Code | Catégorie | Séq. | `core_value` |
|---|---|---|---|
| `GA_AN_LOGT` / `_DOM` / `_EAU` / `_NOUR` | `GA_AIK` | 90-93 | `benefit:housing` / `domestic` / `utilities` / `food` (condition : drapeau de la version) |
| `GA_CNSS_SAL`, `GA_CNAMGS_SAL` | `GA_SOC` | 110, 111 | `cnss_employee`, `cnamgs_employee` |
| `GA_TCS`, `GA_IRPP`, `GA_IRPP_REGUL` | `GA_TAX` | 120-122 | `tcs`, `irpp`, `irpp_regularisation` |
| `GA_FNH_SAL` | `GA_TAX` | 123 | `fnh_employee` (0 tant que la part salariale est 0) |
| `GA_CNSS_PF`, `GA_CNSS_AT`, `GA_CNSS_AVID`, `GA_CNAMGS_PAT` | `GA_EMPLOYER` | 210-213 | `cnss_employer_pf`… |
| `GA_FNH`, `GA_CFP` | `GA_EMPLOYER` | 214, 215 | `fnh`, `cfp` |

`NET` inchangé (`BASIC + ALW + DED`) : les retenues `GA_SOC`/`GA_TAX` (enfants de `DED`) y entrent, les avantages en nature (`GA_AIK`) et charges (`COMP`) non. Test : `NET` Odoo = `PayResult.net` au franc près.

### 5.2 Avantages en nature (décision P1)

Aujourd'hui `GA_AN_*` lisent un montant saisi (dette de 2.2). Le noyau valorise lui-même l'avantage (art. 93, base D-11) à partir de la **nature fournie** : j'ajoute 4 drapeaux sur la version et les règles `GA_AN_*` lisent le noyau ; les types d'entrée `GA_AN_*` disparaissent. Alternative écartée : garder la saisie (le forfait art. 93 ne serait jamais appliqué).

### 5.3 Proratisation (`l10n_ga_prorate`, sprint 0 point 12)

Surcharge de `hr.salary.rule._compute_rule(localdict)` : si `l10n_ga_prorate`, le montant rendu par `super()` est multiplié par `payslip._l10n_ga_paid_ratio()` puis arrondi au franc. Plus simple que d'exposer la règle courante dans le localdict (formules du catalogue inchangées) ; même point d'accroche que celui recommandé au sprint 0.
